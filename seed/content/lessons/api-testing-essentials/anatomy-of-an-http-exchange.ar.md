## لماذا يحتاج المختبرون إلى قراءة HTTP

معظم قواعد العمل في المنتج لا تعيش في واجهة المستخدم. إنها تعيش خلف واجهة برمجية (API): التسعير، والحدود، والصلاحيات، وتغييرات الحالة. تطبيق الويب وتطبيق الهاتف وتكاملات الشركاء كلها تتحدث مع تلك الواجهة عبر HTTP. إذا استطعت قراءة HTTP وكتابته مباشرة، فإنك تستطيع:

- اختبار قواعد العمل قبل وجود أي واجهة مستخدم،
- الفصل بين «الخادم مخطئ» و«الشاشة مخطئة» في ثوانٍ،
- الوصول إلى حالات لا تسمح لك الواجهة بالوصول إليها، مثل الحمولات غير الصالحة، أو معرّفات مستخدمين آخرين، أو الإرسال المكرر، وهذا بالضبط حيث تختبئ العيوب.

## الطلب

إليك طلبًا لإنشاء طلب شراء، مكتوبًا كما ينتقل عبر الشبكة:

```http
POST /v1/orders?dryRun=false HTTP/1.1
Host: api.shop.example
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Accept: application/json
Idempotency-Key: 6f1d2c1e-8b0a-4c1e-9a55-0d7a2e4b9f10

{
  "customerId": "c_1042",
  "items": [{ "sku": "TEA-250", "quantity": 2 }],
  "currency": "JOD"
}
```

| الجزء | مثال | ما الذي تختبره |
| --- | --- | --- |
| الأسلوب | `POST` | هل يُستخدم الأسلوب الصحيح؟ ماذا يحدث مع الأسلوب الخطأ (توقّع 405)؟ |
| المسار | `/v1/orders` | تسمية الموارد، والإصدارات، والشرطة المائلة في النهاية، وحساسية حالة الأحرف |
| سلسلة الاستعلام | `?dryRun=false` | المعاملات المفقودة والمكررة وغير المعروفة والمشوّهة |
| الترويسات | `Authorization`، `Content-Type` | مصادقة مفقودة أو غير صالحة؛ نوع محتوى خاطئ (توقّع 415)؛ غياب `Accept` |
| الجسم | حمولة JSON | الحقول المطلوبة، والأنواع، والحدود، والحقول الإضافية، والمصفوفات الفارغة، والحمولات الضخمة |

## الأساليب، والأمان، وتساوي القوى

الأسلوب يخبر الخادم بنوع العملية التي تقصدها. خاصيتان من مواصفات HTTP تهمّان الاختبار:

- **آمن (Safe)**: الطلب لا يغيّر حالة الخادم. يمكن للعملاء وزواحف الويب والذاكرات المؤقتة إرسال الطلبات الآمنة بحرية.
- **متساوي القوى (Idempotent)**: إرسال الطلب *N* مرة له الأثر نفسه لإرساله مرة واحدة. يمكن للعملاء والوسطاء (proxies) إعادة محاولة الطلبات متساوية القوى بعد انتهاء المهلة.

| الأسلوب | الاستخدام المعتاد | آمن | متساوي القوى |
| --- | --- | --- | --- |
| GET | قراءة مورد أو مجموعة | نعم | نعم |
| HEAD | مثل GET، الترويسات فقط | نعم | نعم |
| POST | إنشاء، أو إطلاق إجراء | لا | لا* |
| PUT | استبدال مورد بالكامل | لا | نعم |
| PATCH | تحديث جزئي لمورد | لا | غير مضمون |
| DELETE | حذف مورد | لا | نعم |

\* كثير من واجهات الدفع والطلبات تجعل إعادة محاولة POST آمنة باستخدام ترويسة **مفتاح تساوي القوى (idempotency key)**. يتذكر الخادم المفتاح ويعيد النتيجة الأصلية للطلبات المكررة. إذا كانت واجهتك توفّر هذا، فاختبره: أرسل الطلب نفسه مرتين بالمفتاح نفسه، وتحقق من وجود طلب شراء واحد فقط ومن تطابق الاستجابتين.

لماذا يهم هذا: شبكات الهاتف تقطع الاتصالات. إذا أعاد عميل محاولة طلب غير متساوي القوى بعد انتهاء المهلة، فقد يُخصم المبلغ من العميل مرتين. عيوب تساوي القوى من أغلى العيوب في التقنية المالية.

## الاستجابة

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/orders/ord_88213
X-Request-Id: req_9b2e71

{
  "id": "ord_88213",
  "status": "pending_payment",
  "total": { "amount": "5.400", "currency": "JOD" },
  "createdAt": "2026-10-11T09:14:03Z"
}
```

الفحص الكامل يغطي الأجزاء الثلاثة:

1. **رمز الحالة:** 201، لأن شيئًا ما أُنشئ.
2. **الترويسات:** `Content-Type` هو JSON؛ و`Location` يشير إلى المورد الجديد؛ ومعرّف الطلب موجود لأغراض الدعم.
3. **الجسم:** البنية صحيحة (الدروس التالية)، و*القيم* صحيحة: المجموع يساوي 2 × سعر الوحدة، والعملة مُعادة كما أُرسلت، والحالة هي الحالة الأولية الموثّقة.

لاحظ `"amount": "5.400"` كنص. كثير من واجهات الأموال تستخدم النصوص لتجنّب أخطاء الفاصلة العائمة، والدينار الأردني له ثلاث منازل عشرية. الاختبار الذي يقارنه بالرقم `5.4` سيكون خاطئًا من ناحيتين.

## رموز الحالة التي يصادفها المختبرون يوميًا

الخانة الأولى تحدد الفئة:

- **2xx نجاح:** 200 OK، و201 Created، و202 Accepted (تستمر المعالجة بشكل غير متزامن)، و204 No Content.
- **3xx إعادة توجيه:** 301/308 نُقل نهائيًا، و304 Not Modified (التخزين المؤقت).
- **4xx خطأ من العميل**، حيث الطلب هو المشكلة:
  - 400 Bad Request: مُدخل مشوّه أو غير صالح.
  - 401 Unauthorized: غير مُصادَق (بيانات اعتماد مفقودة أو غير صالحة).
  - 403 Forbidden: مُصادَق لكن غير مسموح له.
  - 404 Not Found.
  - 405 Method Not Allowed.
  - 409 Conflict: تعارض في الحالة، مثل التكرار أو عدم تطابق الإصدار.
  - 415 Unsupported Media Type.
  - 422 Unprocessable Content: سليم الصياغة لكنه غير صالح دلاليًا.
  - 429 Too Many Requests: تجاوز حد المعدل، غالبًا مع `Retry-After`.
- **5xx خطأ من الخادم**، حيث الخادم هو المشكلة: 500 Internal Server Error، و502 Bad Gateway، و503 Service Unavailable، و504 Gateway Timeout.

قاعدة عامة: **المُدخل غير الصالح يجب ألا ينتج 5xx أبدًا.** إذا استطعت جعل الخادم يعيد 500 بإرسال بيانات سيئة، فهذا عيب، وكثيرًا ما يأتي مع تتبع مكدّس مُسرَّب.

## طلباتك الأولى باستخدام curl

curl مثبّت في كل مكان تقريبًا ويُريك بالضبط ما ينتقل عبر الشبكة.

```bash
# -i includes response headers; -s hides the progress bar
curl -is "https://httpbin.org/get?course=api"

# Send JSON with POST
curl -is -X POST "https://httpbin.org/post" \
  -H "Content-Type: application/json" \
  -d '{"amount": 10.5, "currency": "JOD"}'

# See the full request and response, including TLS details
curl -v "https://httpbin.org/status/418"
```

العملاء الرسوميون مثل Postman أو Bruno يفعلون الشيء نفسه بسهولة أكبر. تعلّم curl على أي حال: إنه ما ستلصقه في تقرير الخطأ كي يعيد المطوّر إنتاج طلبك بالضبط في سطر واحد.

التالي: ستحوّل هذا الفهم إلى مجموعة منظّمة من الاختبارات لنقطة نهاية REST واحدة.
